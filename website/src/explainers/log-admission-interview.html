A

直接答案

快速复习目录 · 全部功能 · Markdown 源稿

把它讲成一个有约束、可恢复的工具结果去噪插件。讲述顺序是问题、流程、取舍、验证和限制。

可直接口述：

Agent 执行构建和测试时，会产生大量进度和重复日志。这些内容可能占用主模型上下文。因此，我在工具执行后增加了可选的日志去噪。

系统先用规则识别候选，并保护失败、摘要和状态等证据。辅助判断器结合任务、候选和保留原文，选择省略、保留或不确定。宿主再检查阈值、任务是否变化和实际节省量。保存原文成功后，才交付带恢复入口的缩短文本。

一个真实主模型参与的合成项目样例中，日志从 8,407 减至 2,122 码点。主模型实际收到了缩短文本，原文也由验收者回读核对。这验证了该样例的去噪和恢复链路。它还不能证明平均 token、费用或任务成功率收益。

B

整体流程

下面展示有语义候选时的主流程。测试日志另有精确重复内容的规则处理路径。

插件通过 tools/post-execute 处理模型可见文本。结构化结果、退出状态和程序返回值保持原语义。原生 spill 与历史 compaction 后续仍可生效。

通用分支处理已识别的进度、重复警告和普通通过信息。测试专用分支保护失败详情、摘要、慢测试和任务点名内容。两者默认关闭；一次结果最多走一个分支。

测试分支识别 Vitest/Jest、pytest 和 Node TAP 的常见文本。它也保护首次警告、skip/todo 和工具状态。完全相同的长失败详情可用首次原文行号引用替换；不同失败必须保留。缺少明确任务依据时，纯进度另有规则处理路径。规则处理同样需要保存原文并达到净节省门槛。

C

判断器究竟看到什么

输入 用途
直接用户消息与最近可见助手意图 提供任务依据，不复制主模型全部上下文
工具名称与命令意图 说明这次日志来自什么操作
确定保留的原文、行号与保护原因 判断候选是否提供新的任务所需事实
候选正文、行号、类别与 ID 明确每题可以处理哪一段
精确重复引用与未提交候选范围 标明证据来源和未展示内容
run_code 的日志外结果文本 单独保留程序结果展示

每个候选对应一个 omit / keep / unknown 选择题。日志内容被标记为不可信数据，不应当作指令。

不能只告诉模型“摘要已保留”。它必须看到摘要原文，才能判断摘要是否覆盖所需信息。其他候选不保证保留，因此不能互相作为省略依据。

设计取舍怎么讲

选择 理由 代价或限制
规则筛选后再做语义判断 限制模型能处理的文本；结合当前任务判断 规则无法识别的格式会旁路
省略原文片段，保留其余原文 避免自由摘要改写事实 压缩空间受保护规则限制
默认省略阈值 0.8 倾向保留不确定内容 未校准，不代表 80% 准确率
先保存原文，再发布省略结果 为省略内容保留恢复入口 原文存储失败则放弃去噪
单次判断，默认等待 4 秒 限制辅助请求等待；故障时继续原流程 成功去噪也会增加判断开销
同时要求净减 300 码点和 10% 把省略标记和恢复提示计入收益 文本节省不等于总费用节省
接入原生工具结果流程 让 Session 与主模型输入能对齐检查 后续原生裁剪仍可能改变可见文本

阈值优先使用返回的 probabilities.omit，缺失时才使用 confidence。真实样例中二者分别是 0.86 和 0.79，按前者达到 0.8 门槛。

F

面试追问

为什么不用正则直接删？ 规则适合识别格式和保护固定证据。某条通过信息是否有用，还取决于任务。用户要求找最快的测试时，通过行里的耗时就有意义。

为什么不让大模型直接总结？ 这个功能选择有约束的省略。它保留未选中片段的原文和顺序，并给出原文恢复入口。自由摘要可能改写事实，也更难把省略结果映射回原始行。

怎么防止误删？ 先限制候选，再提供真实保留证据。低概率和 unknown 都保留；采纳前还核验任务状态。原文保存用于事后恢复，但这些措施不构成零误删保证。

怎么证明不只是 API 调通？ 分别检查判断答案、宿主采纳、最终工具结果和后续主请求。再检查任务产物与原文回读。HTTP 200 只能证明请求成功返回。

为什么受控测试能减 68.7%，真实 180 项测试却没有省略？ 受控样例的概率为 0.79–0.83，7/10 块过线。真实轮次为 0.66–0.71，18 块全部保留。硬门槛解释了省略量差异，但没有解释模型分数的成因。

两轮使用不同日志、任务文字、分组、保留证据和工具来源。它们不是控制变量实验，也没有重复测量。不能直接归因于某一个因素，或把受控压缩率外推到真实任务。真实测试运行无净节省，仍产生了辅助判断开销。

面试可以说：“受控样例验证了省略链路，真实运行验证了触发和保守保留。当前还没有测试日志在自然任务中的稳定平均压缩率。”

G

参数与下一步评估

默认通用日志触发长度为 6,000 码点，测试日志为 4,000。候选块目标为 1,200；序列化请求预算为 48,000。任务与工具意图预算为 12,000。

48,000 是可配置的工程预算。它没有精确执行提供方 tokenizer 容量检查。超预算先减少候选；必要证据仍放不下，就不做语义删除。

未来若评估普遍收益，可比较关闭去噪、仅规则与规则加模型。这是建议，尚未完成。

应测量任务完成率、关键证据误省略率、恢复次数、总 token 和判断时延。总成本需要计入辅助判断请求及主模型后续开销。
